## 回扫窗口与刷新

按用户后续确认，每小时第 7 分只回扫最近 7 天，每天北京时间 02:25 只回扫当前时刻往前一个自然月；窗口按 CODING 提交/创建时间，已有历史镜像不清理，首次只初始化北京时间 2026-01-01 00:00 以来的可见提交记录。超过一个月的旧记录修改或删除不再定期自动对账。

原刷新按钮继续触发增量：本人范围同步本人，团队范围同步当前团队全部参与统计成员，不随日期或成员筛选缩小。正常读取成功扫描上界向前重叠 10 分钟至本轮任务执行时刻；已有任务合并并提升优先级，10 秒内刚成功的请求复用结果，未初始化成员先完成本月，再逐月倒序补齐至起点。排队历史让位于增量；历史段正在运行时，完成后补跑增量，再继续历史。不重复创建同一成员任务。刷新成功（含无新增）更新原同步时间，失败保留旧时间；不会额外核对选中月份的旧记录。

## 成员去重与首次范围调整

后续用户明确要求同一成员 ID 只同步一次、首次范围为北京时间 2026-01-01 00:00 至今并从近到远。当前实现按 CODING 组织 + 成员 ID 建稳定来源；所有 Dev Hub 团队共享。个人 PAT 优先；未绑定则固定选关联且已配置管理令牌的最小团队 ID，不混合多个令牌的项目。凭证或选定管理团队改变时，清除旧镜像及重置进度，同一来源重建；旧版按团队建立的来源只作 RETIRED 审计，不再调度。

首次先本月，之后按月倒序，每段内部最多 100 页 × 1000 条，两次分页稳定后发布该月并推进 history_before。历史段失败保留已发布月份；恢复时重读当前未完成月份，不声称页级断点续传。初始阶段先让所有成员取得近期数据，历史队列优先级 30；同优先级按最近增量时间排序，避免重复发现较小 ID 成员造成新成员长期排队。历史未齐期间报表和明细可读已发布数据，覆盖提示不完整，不判缺勤。

[当前 HTTP 与数据库复核](member-runtime-results.json)：正常 API 创建第二个合成团队，两个团队均包含 101/202/303，分别显示 10.5h；第二团队读取没有新增 CODING 工时请求。SQL 验证每名成员只有一个有效来源，三名成员的 history_before 均到达 1767196800000（北京时间 2026-01-01 00:00）。新列及索引升级在原本的隔离库重复执行成功，原审计保留。

浏览器实际页面观察到 running=true、partial=true 时近期 10.5h 和原同步时间已显示；补齐后 running=false、partial=false。当前截图已打开检查，原布局、图表、记录和刷新图标保持。新增第二个合成团队 ID 2 留在隔离库供查看，不涉及生产数据。
