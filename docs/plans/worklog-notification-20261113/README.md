# 工作台助手：团队工时群通知首版设计

日期：2026-11-13。主仓库：`iw-mixes-server`；协作仓库：`iw-mixes-web-platform`。

状态：用户已确认本方案并于 2026-11-13 授权实施。后端与 Web 已实现；本地自动化、隔离 MySQL/API 和浏览器验收通过，真实 CODING/企微群投递未执行。验收详见 [实施与验收记录](../../acceptance/worklog-notification-20261113-local/README.md)。

## 1. 本版目标与范围

用户最新要求：“还是改用群消息 Webhook吧，然后设计成发多条消息，第一条消息是团队报告，剩下消息就是每个成员的工时登记情况，第一版可以做简单点，也不需要做什么负责人设计了。重新设计下”。本稿取代此前的负责人和个人私聊方案。

已确认并沿用：机器人名称“工作台助手”；指定工作台团队，按工作台日历中的工作日每天北京时间17:00发送；第一条团队报告、后续全员逐人明细；明细包含需求/任务编号、名称和工时任务编号、名称、每笔时长；8h为进度参考，个人请假不计不足，查询失败/不完整不当0h。

首版建议：一个工作台团队配置一个群Webhook，所有内容发送到该群。移除负责人收件人、个人私聊、企微身份绑定、邮箱绑定、邮件和长连接。现有团队管理员负责配置与手动触发，不新增通知负责人角色。不做@映射、任意cron、自由模板、多通道、多Webhook、独立通知中心或历史补发按钮。

影响端：后端iw-external负责配置、当日采集与顺序发送；Web团队详情增加配置区；小程序无改动。

## 2. 配置与使用

建议入口：“团队 → 团队详情 → 工时群通知”，仅现有团队管理员可操作：

| 页面项 | 首版行为 |
| --- | --- |
| 通知开关 | 默认关闭；启用前必须已保存合法Webhook |
| 群Webhook | 粘贴保存后显示“已配置”；支持更换/清除，不回显完整地址 |
| 时间说明 | 固定“工作日17:00，北京时间”，不提供时间编辑 |
| 测试发送 | 向已保存的群发一条连接测试；说明真实发群消息，不发送工时、不自动启用 |
| 立即发送 | 使用已保存配置重新采集今天的完整报告；自动通知关闭、非工作日或 17:30 后也可用，不开启自动通知、不占用定时批次 |
| 最近发送 | 时间、状态、成功条数/总数及脱敏失败原因 |

保存失败保留输入；独立revision防止并发覆盖，冲突提示重新加载。测试按钮防重复点击；切换团队后迟到结果不更新新团队。普通成员无配置读取/修改/测试权限。清除Webhook同时停用；更换地址建议先停用并测试后再开启。管理员转交后由新管理员维护，团队解散后停止发送。

用户在企业微信群添加“消息推送”机器人并命名“工作台助手”，复制Webhook后粘贴；能否创建取决于企业群权限，不能保证绕过企业管控。服务端仅出站调用企微，不配置接收回调、可信回调域名或WebSocket。

2026-11-13 增补（用户已授权）：立即发送为管理员单击操作，异步采集后按原规则顺序投递，页面轮询进度。配置有未保存修改时禁用；同团队已有报告采集或发送时拒绝，10 秒内不重复触发。请求携带 requestId，同一请求重试复用批次；手动批次独立标记 MANUAL，自触发起 30 分钟内发送，复用四表无需新增迁移。配置、成员变化或团队解散仍停止后续消息。参见 [立即发送验收](../../acceptance/worklog-notification-manual-20261113/README.md)。

## 3. 消息内容与顺序

### 第一条：团队报告

以下为合成数据，数字一致；2026-11-13 用户已确认并授权本版排版优化：

```text
研发团队 ｜ 2026-11-13 ｜ 今日工时报告汇总

团队成员：5人；应登记：4人
已达8h：1人
已登记但不足8h：1人（张三）
未登记：1人（李四）
数据异常：1人（王五）
请假：1人（钱七）

接下来逐人发送今日登记明细。
本报告为采集时的登记进度，非最终缺勤结果。
数据更新：2026-11-13 17:00:23
```

首条只放团队级汇总。状态优先判断请假，其次数据完整性，最后按完整数据分为0h、0<h<8h、>=8h。应登记人数=团队人数-请假人数；“数据异常”人数只统计应登记成员异常。请假且取数异常仍归请假，个人明细附异常提示。

已登记但不足8h、未登记、数据异常、请假仅人数大于0时展示，人数后用中文括号列工作台成员名称，以“、”分隔。团队成员、应登记、已达8h始终展示。删除团队工时合计及相关合计不完整说明；数据更新使用北京时间 yyyy-MM-dd HH:mm:ss。

### 第二条起：每位成员一条

```text
研发团队 ｜ 2026-11-13 ｜ 张三

已登记6h，距8h还差2h

项目：业务平台
需求：#1001 优惠券管理
用户故事：#1003 优惠券功能开发
子工作项：#1002 优惠券接口开发
登记工时：2h、1h

项目：业务平台
任务：#1010 订单查询优化
子工作项：#1011 订单索引优化
登记工时：3h
```

所有当前成员均发，按本批成员快照中的稳定顺序：

- 达标：显示已登记时长、已达标和完整明细。
- 完整0h：显示“今日暂无工时登记，距8h还差8h”。
- 请假：显示“今日请假，不计不足”；有实际工时仍列出。
- 失败：显示“数据未获取，无法判断今日登记情况”和脱敏原因，不写0h。
- 部分结果：列已获取记录并标注“不完整，暂不判断是否达到8h”，不计算差额。

通常发送1+成员数条，10人团队为11条。同一成员属于多个启用通知的团队时，各团队各发到自己的群；不做跨团队个人去重，也不向管理员额外发送个人提醒。

个人报告首行是团队、日期、工作台成员名称，不再展示“今日工时”及数据更新时间。项目使用 CODING 显示名称，例如 yuncunzheng 对应“基础服务阿米巴”；事项详情缺少显示名称时，用成员本人可访问项目查询补齐，失败明确提示项目名称暂未获取，不影响已核验工时完整性。

同一项目同一直接事项的多次登记合并一个块，“登记工时：2h、1h”逐笔保留时长。块之间一个空行，各块重复项目及真实父级链。按工时ID去重，明细合计与成员汇总一致；不同项目即使显示名、事项编号相同也不合并。

直接事项和上级按真实类型展示“需求、用户故事、子工作项、任务、缺陷”等及完整编号、名称；不根据深度推断类型。无父级显示“未关联上级需求/任务”；父级无权限或失败显示“上级信息暂未获取”，保留已知事项与时长，不补造缺失层级。仅父级元数据缺失不改变已完整核实的工时总量。Markdown 不可信名称仍转义。

### 超长与节奏

官方[消息推送配置说明](https://developer.work.weixin.qq.com/document/path/99110)已直接核对：Markdown正文最多4096 UTF-8字节，每个消息推送每分钟最多20条。

建议每个Webhook至少间隔4秒，测试也走同一发送队列。10人团队11条消息约40秒发完，另加采集耗时。多个团队共用地址时也共享限流，整批串行，避免团队报告交错。

成员正常一条，超长拆成“张三（1/2）”“张三（2/2）”，连续发完再换下一人。标题、日期、Markdown转义均计入字节上限。不丢明细、不静默截断长名称、不改为仅发链接；长标题必要时分成带续文标记的文本片段。不使用@all，不获取企微userid或手机号。

## 4. 统计口径

- 共享工作日历为准：调休工作周六发送，设为休息日的周一不发。个人请假不取消团队发送。
- 17:00触发采集，按北京时间CODING StartAt归属；补登历史日期不计今日。消息标记实际更新时间，不宣称精确重建17:00:00的远端快照。
- 每人用本人备份PAT和身份查询，不依赖浏览器在线、不用管理员PAT替代成员权限。
- 复用完整分页、工时ID去重和删除事项排除。当前异步删除检查需有界等待并重读修订结果；未核验完标记待核验，不按完整结果判断。
- 报告和全部明细使用同一批成员/工时快照，发送中补登不修改该批内容。17:00是登记进度，不更改既有只算到昨天的缺勤接口。

## 5. 最小后端方案

流程：工作日17:00 → 读取启用配置/成员 → 采集当日快照 → 生成报告及成员消息 → 落库 → 顺序发送 → 记录结果。

采用Spring定时任务和MySQL记录，不增MQ或独立服务。仅固定类型WORKLOG_DAILY_REPORT和一个Webhook适配入口；未来新增通知类型时复用配置和发送记录，不提前做规则引擎。

| 数据（计划新增） | 主要字段/约束 |
| --- | --- |
| 团队配置 | codingTeamId、workbenchTeamId、enabled、加密Webhook、地址指纹、revision、修改人/时间；每团队唯一 |
| 每日批次 | 团队、日期、类型、配置revision、成员/日历/请假/工时快照、采集时间、状态、成功/总条数；团队+日期+类型唯一 |
| 批次消息 | batchId、顺序号、SUMMARY/MEMBER、成员ID、分段号、固定正文、状态、尝试次数、脱敏错误；批次+顺序号唯一 |

先落库再发送，通过唯一键和原子领取防并发重复。建议保存最近30天，仅展示最近一次结果，不做独立历史检索。手动发送仅重新采集今天，不提供历史批次重放。

定时通知只触发当天17:00一轮，未运行则不自动补历史日报；已落库定时批次可在当天17:30前续发尚未发送的消息，超时标过期。手动批次按触发起30分钟计算窗口。

严格先首条成功再成员顺序发送。明确可重试失败最多重试2次，仍遵守限流；永久失败或耗尽次数则停止剩余消息，显示已发x/y。HTTP成功还须检查企微业务errcode；全部成功才标完成。超时或重启落在“已提交但未记录回执”区间，标记结果未知并暂停，不盲重发。平台受理不等于已读，不能宣称外部严格只出现一次。

每条发送前确认团队存在、配置仍启用且revision未变；停用、更换地址、解散后停止旧批次，不把旧快照发往新地址。成员移除后停止含该成员的旧批次；新成员下一批加入，不在本批临时追加。

Webhook只接受HTTPS、固定域名qyapi.weixin.qq.com、固定路径/cgi-bin/webhook/send及合法key；不跟随重定向，不接任意URL。地址加密保存、读取仅返回已配置标记，日志/截图不输出完整URL或key。地址指纹用于限流而非发送。首版不读取群名或群成员，测试以实际群收件确认。

API草案统一前缀/external-service/api/zhaogang：

- GET /teams/{teamId}/worklog-notification：管理员查已配置标记、enabled、revision、固定时间、最近批次，不返回完整Webhook。
- PUT /teams/{teamId}/worklog-notification：enabled、revision、可选新webhook；省略保留，显式clearWebhook清除并停用，不能同时传新地址和清除。
- POST /teams/{teamId}/worklog-notification/test：当前revision，使用已保存地址，单条测试，独立防重复和限流，不影响每日批次。

## 实施选择

- 团队详情由现有管理员配置，四条 API 位于 `/teams/{teamId}/worklog-notification`，包含立即发送。配置独立 revision；默认关闭，地址加密存储、不回显，清除同时停用。
- 使用专用 Spring `ThreadPoolTaskScheduler` 实例，不替换其它业务的默认调度器。17:00 只创建当天定时批次；单团队采集最多等待 120 秒。未完成采集的批次失败且不发送；定时消息在 17:30 前续发，手动消息自触发起 30 分钟内续发，不自动补历史日期。
- 当日读取复用现有分页、StartAt 过滤和去重；直接事项同步核验，综合所有成员证据后记录唯一可信删除。父级按真实链最多读取 16 层，正文使用完整编号和名称；未加 CODING 外链。
- MySQL 保存配置、脱敏快照、逐条消息、共享地址通道。每个地址整批顺序发送，发送完成后至少间隔 4 秒；明确限流/暂忙最多重试 2 次，每次至少等待 60 秒。超时、响应不明或中断进入 UNKNOWN，后续消息停止。
- 测试发送复用同一持久化队列，只入队一条连接消息；需当前保存版本，10 秒冷却，并禁止同团队重复排队测试。测试批次有效期 10 分钟，不修改通知开关。
- 记录保留 30 天；清理在北京时间 03:15 执行。所有时间窗口用北京时间，数据库调度时刻使用 epoch 毫秒。
- Webhook 加密密钥从既有 session-key 按用途派生；更换该密钥后需重新保存 Webhook。请求正文日志对本接口精确排除，请求格式错误也不记录原始正文。
