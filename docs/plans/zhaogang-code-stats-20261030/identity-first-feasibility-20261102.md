# Git 身份优先统计：可行性调研（2026-11-02）

状态：用户确认并授权实施后，代码及本人十月真实验收已完成，详见 [本轮实施与验收](../../acceptance/zhaogang-code-stats-20261030/identity-first-20261102.md)。下文“本轮调研”描述的是先前调研阶段。

## 用户提出的目标

- 根据每个成员本人 PAT 默认初始化作者名、邮箱两个 Git 身份，支持后续新增与删除。
- 个人与团队的提交次数、行数和其他统计，都先按 Git 身份筛选。
- 后续用户明确补充：按新设计实施后，移除个人代码页整段“扫描范围内尚有 X 次提交未归属作者”提示及其说明、绑定引导，不按数量是否为零显示，也不替换为类似未匹配告警；保留顶部“我的 Git 身份”作为身份查看和增删入口。
- 团队成员可按各自身份并发读取。
- 若 CODING API 不支持按身份过滤，应回到用户确认规则，不能自行退回全量读取方案。
- 已确认特殊仓库 online.base.apijar.service 仍仅统计提交次数；合并提交仍按既有规则排除。

## 官方接口核对

2026-11-02 实际访问 [CODING OpenAPI](https://coding.net/help/openapi)，从其 HTML 的 DOCUMENT_YAML_URL 加载 [当前官方规范](https://assets.codehub.cn/document/openapi/353b949e0b605519499f4c684f185b2649231b9f.yaml)。规范 SHA-256：4464a3266cbb631eb93c2aa0fd3e75786aaab3fc3036a2618e3e42d31ac6a89d。只提取相关接口结构，不复制认证示例。

| 接口 | 已确认能力 | 限制 |
| --- | --- | --- |
| DescribeCodingCurrentUser | 返回当前用户 Id、Name、Email、GlobalKey 等 | Name 是 CODING 账户姓名，不保证等于历史 Git AuthorName；Email 也不保证覆盖历史 Git 邮箱 |
| DescribeGitCommitsInPage | DepotId/DepotPath、Ref、StartDate/EndDate、PageNumber/PageSize、Path、KeyWord | 没有作者名、作者邮箱、作者 ID 筛选参数；KeyWord 是提交信息关键词 |
| DescribeGitCommitInfos | 同类提交列表请求参数 | 同样没有作者筛选 |
| DescribeProjectDepotCommits | ProjectId、Id、DepotType、Branch | 没有作者筛选 |
| DescribeGitContributors | 仓库/分支贡献者查询 | 请求没有作者或起止日期，不能代替指定月份的提交明细及逐 SHA diff |
| DescribeGitCommitDiff | 按仓库及 SHA 取 diff | 必须先取得目标 SHA，不能按作者直接获取月度行数 |

同时检查规范中全部 151 个“代码托管相关接口”的请求字段，没有找到可满足“任意 Git 作者名/邮箱 + 指定月 + 全部分支提交明细”的公开查询。合并请求的 CreatorEmails 等字段仅筛选 MR，不等价于 Git 作者提交。

结论限于当前公开、受支持接口；没有实际调用未文档化的 Author/AuthorEmail 参数，不宣称参数一定被拒绝或某个内部接口绝对不存在。HTTP 200 本身不能证明未知过滤参数生效。

## 可实现部分及现状差距

1. 默认双身份可以实现：使用每位成员自己的 PAT 查询 Name/Email，初始化两个身份。当前个人扫描只自动补邮箱；团队还会按当前范围内唯一用户名生成姓名映射，尚非用户提出的统一模型。
2. 自助新增和删除可以实现：当前个人支持新增自定义邮箱/姓名，但 AUTO 身份不允许删除，且扫描会重新执行自动映射。新方案必须明确初始化与日常扫描分开，删除后保留初始化/删除标记，防止下一轮扫描自动恢复。
3. 个人与团队复用成员身份可以实现：当前映射按 SELF 和 WORKBENCH_TEAM 分开。建议由成员维护一份身份集合，个人和所在团队引用相同集合，团队权限继续约束可见成员及仓库。
4. 所有 KPI 先筛身份可以实现：命中任一有效身份后才进入去重、提交计数、行数、活跃日、仓库与图表聚合。姓名或邮箱命中同一条提交不能重复计数；成员之间身份冲突不能直接把同一提交计入两人。此 OR 匹配与当前“邮箱映射优先、姓名回退”不同，是需落到最终设计的变化。
5. 按成员有限并发可以实现：已有按 PAT 的并发闸门及提交/diff 全局 QPS，仍须保留。公开规范提示单团队单接口每秒最多 30 次；更多 PAT 不等于能无限并发。现有提交/diff 默认全局各 25 QPS。
6. 不能按当前公开接口直接实现远端先筛作者。若对每个成员分别遍历同一仓库/月份，却不能携带有效作者过滤参数，会重复读取相同提交，可能比当前更慢。

## 已确认的读取路径

确认依据：2026-11-02 用户对“先按月份读取提交元数据，收到后立即按已绑定 Git 身份过滤，只保存命中的提交、只为命中的提交拉取 diff”的问题回复“接受元数据本地过滤（推荐）”。这是设计选择确认，本轮继续保持调研范围。

A（已确认采用）：远端按仓库、分支、月份读取轻量提交元数据，每页返回后立即按有效 Git 身份匹配；仅保存命中提交，仅为命中提交读取 diff。团队共享同一可见范围内的分页工作，按成员身份分发，独有仓库可并发；不再把其他作者的总提交显示为本人“未归属告警”。必须明确：该方案仍会从 CODING 接收到其他作者的元数据，无法满足“远端只返回本人提交”的严格要求。

B（未采用）：如果“远端先筛作者、不接收其他作者元数据”是硬要求，则暂缓扫描改造；需 CODING 提供/确认可支持的作者筛选 API，再做有命中与无命中对照、姓名/邮箱、多身份 OR、分页/总数及全分支覆盖验证。

Git mirror/本地 git log 虽能按作者筛选，但需要下载仓库对象、磁盘和凭证生命周期管理，且并不避免先传输其他作者历史，本轮不作为已选方案。

## 后续设计必须覆盖

- 默认身份初始化时机、缺失 Name/Email 的明确状态、PAT 更换/账户信息变更，以及默认身份被删除后不自动复活。
- 姓名/邮箱 OR 命中、同名及跨成员冲突；不得把 CODING 昵称直接视为历史 Git 身份的证明。
- 身份新增后历史月重新筛选/补数，删除后立即排除；旧结果缓存、扫描快照与身份版本联动，避免被过滤过的快照导致新身份漏数。
- “只保存命中提交”同时约束 MySQL 提交记录和 Redis 分支快照。当前快照包含所有作者的提交，实施时须变更缓存格式/版本；身份增加后不能直接复用旧身份集合过滤的快照，否则会漏数。未命中元数据仅在读取/过滤所需内存中短暂使用，不新增全作者持久化副本。旧快照与旧全作者记录的迁移/清理需先备份并列明范围，不在调研阶段执行。
- 当前邮箱与姓名键仅存哈希，作者名展示还做脱敏，不能直接恢复成远端搜索参数；若将来支持服务端按身份筛选，需另行确定可用于查询的原值安全存储方式。
- 仓库+SHA 去重、跨分支去重、合并排除、特殊仓库仅计次数、部分成功与扫描进度继续保留。
- 修改涉及 iw-external 的身份模型/解析、查询、扫描与快照缓存、Mapper，以及 Web 身份弹窗/提示与统计类型；不涉及微信小程序。
